maubase

A Firebase/Supabase alternative you actually own.

Auto-generated REST APIs, OAuth 2.1 for your own users (MCP clients included), realtime subscriptions, file storage, and an admin UI — all compiled into one cgo-free Go binary you build, run, and back up yourself. No dashboard to log into that isn't yours.

$ go build -o maubase ./cmd/maubase && ./maubase
listening on :8080 (db: data/maubase.db)
  • Go 1.27
  • SQLite, no cgo
  • Single binary
  • Self-hosted, not a cloud account

What ships in the binary

Every table becomes an API. Every user gets a session. Nothing calls home.

/api/data/{table}

Auto REST

Every table that isn't reserved for maubase's own use becomes a full CRUD API the moment it exists — whether you created it with a migration, the admin UI's create-table form, or a raw CREATE TABLE in SQL Studio. Rows are scoped to whoever created them through an owner_id column, checked on every request: nobody sees a row they didn't create unless you say otherwise with an access rule.

shell
$ curl -X POST localhost:8080/api/data/posts \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title": "Hello"}'
{"id": "b7e1...", "title": "Hello"}

$ curl "localhost:8080/api/data/posts?limit=10"
[{"id": "b7e1...", "title": "Hello"}]

$ curl -X PATCH .../api/data/posts/b7e1... \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title": "Edited"}'

/oauth/*

OAuth 2.1 server

Every deployment is also its own authorization server. Your users can grant a third-party app — an MCP client, a script a teammate wrote, a mobile app you didn't build — scoped access to their own data, the same flow behind any "Sign in with..." button. PKCE is mandatory, and refresh tokens rotate on every use; replaying a stale one is treated as theft and revokes the whole grant chain.

shell
GET /oauth/authorize
  ?response_type=code&client_id=...
  &redirect_uri=...&scope=records:read
  &code_challenge=...
  &code_challenge_method=S256

$ curl -X POST localhost:8080/oauth/token \
  -d grant_type=authorization_code \
  -d code=$CODE \
  -d code_verifier=$VERIFIER \
  -d client_id=$CLIENT_ID
{"access_token": "...", "expires_in": 3600}

/admin/ui

Admin UI

A server-rendered admin panel ships in the same binary as the API — nothing separate to deploy, no static assets to host, no extra API keys just to look at your own data. Create tables live, browse and edit rows, manage owner accounts, and read the audit log, all from routes the binary already serves.

  • /admin/ui/tables/newCreate a table — live, no restart
  • /admin/ui/sqlSQL Studio — raw queries against the live database
  • /admin/ui/usersBrowse and edit customer rows
  • /admin/ui/audit-logEvery login, create, and delete — who, when

/api/realtime

Realtime

One WebSocket endpoint delivers created/updated/deleted events for any auto-REST table you're allowed to read. Fan-out is single-process by default, the right answer for a small deployment; set MAUBASE_REDIS_URL once you're running more than one instance and need events to reach every process.

js
const ws = new WebSocket(
  "ws://localhost:8080/api/realtime" +
  "?access_token=" + token
);
ws.onopen = () => ws.send(JSON.stringify({
  type: "subscribe", collection: "posts"
}));
ws.onmessage = (e) => console.log(e.data);
// { type: "created", collection: "posts" }

/api/storage/files

File storage

Upload and download endpoints that sit right next to the rest of the API, gated by the same files:read/ files:write OAuth scopes as everything else — no separate object-storage service, no separate credentials to issue. A file belongs to whoever uploaded it, the same ownership model as any other row.

shell
$ curl -X POST .../api/storage/files \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@report.pdf"
{"id": "9c4a...", "filename": "report.pdf"}

$ curl .../api/storage/files/9c4a.../content \
  -o report.pdf

_policies

Row-level access rules

owner_id gets you per-row ownership for free; _policies gets you the rest. Declare, per table and per operation, whether a collection is owner-only, shared read-only, or denied outright — enforced the same way ownership is, without hand-rolling middleware for it.

/api/auth/social/*

Social login

"Continue with Google" and "Continue with GitHub," wired into the exact same session system as email and password — not a bolt-on identity provider off to the side. Each provider is independently optional: leave its client ID unset and that one route 404s, nothing else changes.

shell
$ curl -i localhost:8080/api/auth/social/google
HTTP/1.1 302 Found
Location: https://accounts.google.com/o/oauth2/v2/auth?...

maubase migrate

Migrations CLI

Beyond scaffolding and applying migrations (see the quickstart below), the same command reverts, redoes, and jumps straight to a specific version — and diff catches schema drift introduced outside any migration file, like a table someone created by hand in SQL Studio.

shell
$ maubase migrate diff
unexplained  widgets  (no migration explains it)

$ maubase migrate down
reverted 0004_add_comments_index.sql

$ maubase migrate to 0002_create_posts.sql
reverted 0004_add_comments_index.sql
reverted 0003_create_comments.sql

Why not just use Supabase

Same shape of tool. Different owner.

“Move it, back it up, read the SQL — no migration off someone else's platform.”

Firebase and Supabase are a great deal, right up until you need your data somewhere they don't operate, a compliance boundary they don't meet, or a bill you didn't expect. maubase gives you the same shape of tool — auto-REST, auth, realtime, storage — compiled into one binary that runs on hardware you control.

From zero to an API

Four commands in, one table live.

No dashboard to click through first — the schema, the migration history, and the running server are all right here in the terminal.

shell
$ maubase init
created migrations
created migrations/0001_init.sql
created .env.example
created .gitignore

$ maubase migrate new create_posts
created migrations/0002_create_posts.sql
# edit it, add your CREATE TABLE

$ maubase migrate up
applied 0002_create_posts.sql

$ curl -s localhost:8080/api/data/posts
[]
